Why I Replaced Redis & MongoDB with SpacetimeDB Real-Time Streaming Reducers

Published2026.09.17
AuthorMax (McMmax) (McMmax)
Reading Time8 min read
PlatformGitHub Pages SSG
#spacetimedb #architecture #systems

If you have ever built a high-concurrency multiplayer platform or low-latency simulation engine, you know the conventional industry dogma: put an in-memory cache like Redis in front of your service, back it with a document or SQL store like MongoDB or PostgreSQL, stitch them together with asynchronous message queues like Kafka or Redis Streams, and pray your cache invalidation logic doesn't tear your application apart.

After years of debugging race conditions, desynchronized inventories, dual-write split-brain anomalies, and multi-millisecond network hops in production, I tore that entire multi-tier stack out. In our network architecture, traditional databases have been completely replaced with SpacetimeDB running real-time streaming WebAssembly reducers.

Here is an architectural post-mortem on why traditional databases fail under real-time constraints, and how streaming reducers fundamentally altered how we synchronize state across our distributed fleet.

1. The Triple-Tier Database Trap

Consider what happens when a player performs an action in a high-frequency simulation (such as transferring an enchanted sword between a chest and an inventory, taking knockback from an arrow, or updating an economy balance). In the traditional architecture: 

┌────────────────┐      RESP      ┌───────────────┐     Write-Back    ┌─────────────────┐
│   Game Server  │ ─────────────► │  Redis Cache  │ ────────────────► │  MongoDB / SQL  │
│   (Java / Go)  │ ◄───────────── │  (In-Memory)  │                   │  (Durable Disk) │
└────────────────┘   Round-trip   └───────┬───────┘                   └─────────────────┘
        │                                 │
        ▼                                 ▼
   Kafka / Redis Streams (Pub/Sub) ──────── Event Bus to Fleet Gateways

This design introduces five fatal vulnerabilities:

  • Dual-Write Incoherence & Cache Invalidation: A write to Redis succeeds, but the asynchronous persistence worker to MongoDB dies or times out. Redis now contains phantom state that never persisted to disk. Under server failure or network partitions, state rolls back to an arbitrary checkpoint, creating classic "item duping" or "balance rollback" exploits.
  • BSON Document Race Conditions: Storing player profiles and inventories as massive nested BSON documents (e.g., profile.inventories[].slots[]) means any concurrent modification requires complex array filters or whole-document overwrites. Two concurrent actions across different instances overwrite each other's changes.
  • The Serialization Tax: Every single state transition requires serializing Java/Go structs into RESP strings, deserializing on the Redis end, re-serializing into BSON/JSON for MongoDB, and parsing it back out. At 200Hz scheduling cadences, serialization alone accounts for upwards of 35% of total CPU time and triggers catastrophic GC pauses.
  • Fail-Open Seams in Anticheat & Security: If an external database query experiences jitter (e.g., a 40ms tail-latency spike), the game engine must choose between blocking the game tick thread (inducing server lag) or failing open (allowing the action without confirmation). Cheaters deliberately exploit this boundary by inducing network bursts to bypass security checks.

2. The Paradigm Inversion: The Database IS the Server

SpacetimeDB inverts the entire relationship between compute and storage. Instead of deploying an application server that queries a distant database over a network socket, the database engine itself executes your application logic.

You write your business logic as deterministic reducers in Rust. SpacetimeDB compiles your code into WebAssembly and executes it directly inside the memory space of the relational table store. 

#[spacetimedb::reducer]
pub fn transfer_item(
    ctx: &ReducerContext,
    source_slot_id: u64,
    dest_slot_id: u64,
) -> Result<(), String> {
    // 1. Fetch source slot via indexed B-tree lookup (sub-microsecond)
    let mut source = InventorySlot::filter_by_slot_id(&source_slot_id)
        .ok_or("Source slot does not exist")?;

    // 2. Security validation: caller must own the container
    let container = Container::filter_by_container_id(&source.container_id)
        .ok_or("Container not found")?;
    if container.owner_spacetime_id != ctx.sender_id {
        return Err("Permission denied: unauthorized container access".into());
    }

    // 3. Atomically reassign slot reference
    let mut dest = InventorySlot::filter_by_slot_id(&dest_slot_id)
        .ok_or("Destination slot does not exist")?;

    let moved_item_id = source.item_instance_id;
    source.item_instance_id = None;
    dest.item_instance_id = Some(moved_item_id);

    InventorySlot::update_by_slot_id(&source_slot_id, source);
    InventorySlot::update_by_slot_id(&dest_slot_id, dest);

    Ok(())
}

The Single Deterministic Transaction Lane

Reducers execute in a single-threaded deterministic WASM runtime. Because the tables reside directly in physical RAM within the same process, transaction execution is measured in microseconds, capable of processing over 250,000 transactions per second on bare-metal hardware.

More importantly: every reducer is an atomic ACID transaction. If any validation check fails or an error is returned, the entire transaction rolls back instantly. There is no such thing as a partial commit, no dangling lock, and no desynchronized cache. It is architecturally fail-closed.

3. Eradicating Message Brokers: Transient Event Tables

In a distributed gaming network, servers constantly emit high-frequency ephemeral telemetry: combat knockback vectors, damage calculations, line-of-sight raycasts, and anticheat suspicion signals.

In the old world, routing these required deploying a dedicated Kafka or Redis Streams cluster. You had to configure consumer groups, manage offsets, and write background garbage collectors to trim expired stream keys before memory exhausted.

In SpacetimeDB, we completely replaced Redis Streams using Transient Event Tables: 

#[spacetimedb::table(name = knockback_event, public, event)]
pub struct KnockbackEvent {
    #[primary_key]
    pub event_id: u64,
    pub target_spacetime_id: u64,
    pub impulse_x: f32,
    pub impulse_y: f32,
    pub impulse_z: f32,
    pub timestamp_us: u64,
}

How Real-Time Streaming Reducers Work:

  1. Insert during Reducer: When combat logic resolves in a reducer, it inserts a row into the knockback_event table.
  2. Streaming Binary SATN Wire Synchronization: The SpacetimeDB engine immediately computes the binary diff and broadcasts the row delta over WebSockets via Binary SATN (BSATN) to all subscribed game nodes (proxies, edge gateways, visualizers).
  3. Automatic Transaction Evaporation: Because the table is marked event, the row is automatically deleted from memory upon transaction commit.

Zero bytes are written to persistent disk commitlogs. Zero unpruned rows accumulate in memory. Connected clients receive the live delta within microseconds of transaction execution, with zero message broker infrastructure.

4. Partitioned 200Hz Scheduling: Taming the Global Tick

When we initially upgraded from legacy databases to SpacetimeDB 2.5, we made a classic novice mistake: we registered a single global scheduled reducer, world_tick(), that ran every 50ms and iterated across all online players in the database.

As our concurrent player count grew past 500, that single reducer began taking >25ms to execute. Because SpacetimeDB guarantees strict serial execution, that one global loop occupied over 50% of the single WASM transaction lane, stalling incoming combat and movement reducers.

The Solution: Partitioned Scheduled Instance Rows

We restructured our tick model into Partitioned Regional Schedulers:

  • Instead of one global loop, every distinct game region, arena, or prison mine instance registers its own independent scheduled row in a scheduled_instance_tick table.
  • Each scheduled reducer queries strictly indexed sub-trees (e.g. .filter_by_region(region_id)) via in-memory B-tree indexes.
  • Transactions run in parallel chunks, keeping every individual scheduled reducer execution under 15 microseconds.

5. Hot vs. Cold Domain Segmentation

To prevent high-frequency combat telemetry from interfering with durable player accounts, we segregated our database into strict operational domains:

Module Update Cadence Key Responsibilities Storage Lifecycle
stdb-hot 200Hz Scheduler / 20Hz Tick Continuous collision detection (swept AABB), player velocity vectors, knockback impulses, Polar 16³ voxel collision sections. In-Memory / Ephemeral Event Tables. Bounded RAM footprint.
stdb-cold Event-Driven / Transactional Player identities, profiles, sequential u64 spacetime_id, RBAC permission nodes, disciplinary logs, and economic balances. Append-Only Durable CommitLog with strict zero-loss guarantees.
stdb-inventory Transactional Fully normalized relational slots (-1..40, 100+), item instances, enchantment arrays, container transfer verification. Relational ACID persistence with zero duplication vulnerability.

Sequential u64 IDs vs. 128-bit UUIDs

One of our biggest wins was eliminating Mojang 128-bit UUIDs as database keys. High-frequency random UUIDs fragment B-tree index pages and wreck CPU L1/L2 cache lines. We mapped all incoming identities at the network gateway to a sequential u64 spacetime_id. Index lookups became single-cycle pointer offsets.

6. Relational Inventories: Eliminating Item Duplication

In Minecraft server development, item duplication bugs have plagued servers for fifteen years. Almost every dupe stems from the same architectural flaw: inventories stored as un-normalized binary NBT blobs or MongoDB BSON arrays.

When a player drops an item and simultaneously triggers a proxy disconnect, one thread writes the inventory while another thread handles the drop entity. Because external databases cannot execute an atomic lock spanning the player state, the ground entity, and the proxy session, both actions succeed.

In our SpacetimeDB relational inventory schema: 

CONTAINER (container_id [PK], owner_spacetime_id)
    │
    └──► INVENTORY_SLOT (slot_id [PK], container_id, slot_index, item_instance_id [Unique])
              │
              └──► ITEM_INSTANCE (item_instance_id [PK], item_type_id, amount, durability)
                        │
                        ├──► ITEM_ENCHANT (enchant_id, level)
                        └──► ITEM_KILL_STAT (victim_spacetime_id, killed_at)

Every item instance has an immutable 64-bit ID. An item_instance_id can exist in exactly one slot row at any given microsecond. Any reducer attempting to move an item must atomically verify the source slot, mutate the container reference, and commit. If a player attempts a concurrent disconnect or double-click exploit, the second reducer immediately fails validation. Item duplication is eliminated by architectural construction.

7. Production Reality & Benchmark Results

Running this architecture in production across our network yielded night-and-day operational improvements:

  • End-to-End Latency: Traditional Redis-cache + Mongo writeback pipeline averaged 18ms – 42ms p99 latency under combat load. With SpacetimeDB WASM reducers, p99 transaction commitment dropped to under 280 microseconds.
  • Zero Cache-Aside Bug Reports: We eliminated over 4,000 lines of glue code responsible for caching, invalidation timers, distributed Redis locks, and MongoDB reconnect loops.
  • Infrastructure Footprint: We shut down 6 Redis nodes, 3 MongoDB replica sets, and 2 Kafka broker instances, replacing them with a single compiled SpacetimeDB container backed by our custom Rust edge proxies.

Traditional databases were designed for an era where application servers and storage lived on separate machines connected by slow networks, exchanging ad-hoc SQL strings. In modern high-frequency systems where microseconds matter, executing compiled reducers directly inside memory-resident relational state is the only architecture that makes sense.
